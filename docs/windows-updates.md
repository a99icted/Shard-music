# Windows updates

The desktop app checks `https://api.github.com/repos/a99icted/Shard-music/releases/latest` five seconds after launch and every six hours while notifications are enabled. Manual checks work regardless of that preference. Turning off notifications persists in the user's existing `settings.json` and does not prevent manual updating.

Only a newer stable `vMAJOR.MINOR.PATCH` release with both `Shard-MAJOR.MINOR.PATCH-Setup-x64.exe` and `Shard-MAJOR.MINOR.PATCH-Setup-x64.exe.sha256` is eligible. Drafts, prereleases, older versions, mismatched asset URLs and missing checksums cannot trigger installation. Files must belong to the same release of the official repository. The updater verifies the exact advertised size and SHA-256 before launching anything.

Update requires a confirmation dialog. Downloads and hashing run in the background; cancellation removes the incomplete attempt. If library writes or synchronization are still active when downloading finishes, the verified installer stays ready in this session and the user can install after those operations finish. Quitting the app flushes settings and playback state normally. Inno Setup's update mode waits up to two minutes for that process to exit before modifying files, installs into the registered current installation, and restarts the application. The isolated test edition does not update into the stable edition.

The installer is retained under a unique `%TEMP%\shard-update-*` directory with `install.log` for diagnosing installation failures. User music and settings are outside the installation folder and are never part of the installer payload or deletion rules.

Manual installs also close a running Shard before Restart Manager checks file locks. `PrepareToInstall` locates Shard tray windows and verifies the owning executable's full path against the selected installation folder. It posts `WM_QUIT` to that GUI thread and waits for process exit. This is compatible with 0.1.7: GPUI runs the normal shutdown hooks when its message loop exits, flushing playback statistics and preferences. `WM_CLOSE` alone only hides that edition in the tray. No process is forcibly terminated, and instances from other install folders are left alone. If shutdown does not finish within two minutes, installation stops with instructions to quit Shard from its tray menu.

To publish a new update, bump Cargo.toml and both lock files, add `docs/releases/vMAJOR.MINOR.PATCH.md`, and push a matching stable version tag. `.github/workflows/windows-release.yml` tests the core, packages and verifies the Windows installer, uploads the installer and checksum into a draft, and publishes only after all assets are uploaded. It refuses to replace an already published release. The workflow can also be run manually for an existing matching tag. No release is published merely by building locally.

Existing 0.1.7 and earlier clients have no updater, so they need to install 0.1.8 manually once. Further updates use the flow above. The initial implementation supports the per-user Windows installer; portable/development runs can check release availability and open release notes but cannot replace an unrelated installed executable.

Validation: `cargo test --locked --no-default-features --lib -- --test-threads=1` covers release selection, version ordering, official asset URLs, checksums, truncation, oversized downloads, cancellation, and notification persistence. After packaging, `scripts/test-windows-updater.ps1` compiles the production installer script with an unrelated temporary AppId and a tiny fixture. It verifies the parent-exit wait, silent install, automatic restart, and unchanged external data, then uninstalls only that fixture. It retains its temporary diagnostic files and writes `dist/windows-updater-smoke-verification.json`. To inspect the UI on a temporary library, run `cargo run --example layout_preview -- 1100 760 --updates --update-available`; the fake release is available only in debug builds and has no download URLs. Add `--collapsed` to check the collapsed sidebar.
